# 專案需求文件（基本版）

## 1. 專案目標
建立一個網頁版對談系統，在時程緊迫情況下，先完成可用的核心通訊功能，支援個人與群組對談。系統需提供統一外部整合 API，讓其他網站或業務系統可透過 API 與本對談系統溝通，不另為 ERP 或任何單一來源系統建立專屬產品分類或專屬界面。

## 2. 功能需求

### 2.1 訊息與內容傳送
1. 使用者可在聊天室傳送純文字訊息，內容包含 `http://` 或 `https://` 網址時需在訊息中顯示為可點擊連結。
2. 使用者可在聊天室傳送圖片檔案，支援 `.jpg`、`.jpeg`、`.png`、`.webp`、`.gif`、`.heic`、`.heif`。
3. 使用者可在聊天室傳送一般檔案，至少支援：
   - `.doc`
   - `.docx`
   - `.xls`
   - `.xlsx`
   - `.ppt`
   - `.pptx`
   - `.pdf`
   - `.txt`
   - `.csv`
   - `.rtf`
   - `.md`
   - `.odt`
   - `.ods`
   - `.odp`
   - `.pages`
   - `.numbers`
   - `.key`
   - `.zip`
   - `.rar`
   - `.7z`
4. 聊天室需顯示訊息時間、傳送者、訊息類型（文字/圖片/檔案）。
5. 一般檔案單檔上傳大小上限為 `40MB`。
6. 上傳大小上限需在使用者介面明確註記。
7. 桌機版任一訊息泡泡需支援右鍵操作選單，至少包含引用回覆與收回；引用回覆不分發送者，收回僅允許處理自己送出的訊息。引用已含回覆的訊息時，回覆摘要只取該訊息本身內容，不遞迴帶入更早引用鏈。

### 2.2 對談模式
1. 系統需支援「一對一」個人對談。
2. 系統需支援「群組對談」。
3. 使用者可建立群組並邀請其他成員加入。
4. 群組內成員可共同收發文字、圖片與檔案訊息。
5. 群組權限角色分為：`owner` / `admin` / `member`。

### 2.3 帳號與登入整合（外部系統接入）
1. 系統需提供對外 API 介面，供其他網站或業務系統呼叫。
2. 外部系統可透過 API 進行使用者「自動註冊」。
3. 外部系統可透過 API 進行使用者「自動登入」。
4. 自動註冊 / 登入流程需可回傳成功或失敗結果與原因碼。
5. 使用者帳號唯一識別以 `source_system` + `external_user_id` 為準。
6. 外部系統自動登入採帳號密碼流程：外部系統呼叫登入 API 時需提供帳號、密碼與裝置識別，驗證成功後由系統回傳可用於登入的憑證或登入結果。
7. 外部整合能力為統一 API 契約，不應針對 ERP 或其他單一系統另開專屬聊天介面。
8. 外部系統接入端點需支援 `Authorization: Bearer <shared-token>` 驗證。
9. 外部系統接入端點需支援 request `timestamp` 與 `signature` 驗證，以降低重放與偽造風險。
10. `timestamp` 需使用 Unix 秒數，並限制在可容許時間誤差內。
11. `signature` 需以 `HMAC-SHA256` 驗證請求 method、path、timestamp 與原始 request body。
12. 密碼長度需為 4 到 20 碼，只允許英文、數字與特殊符號，不允許空白與其他語系字元。
13. Web 入口需依登入狀態導向：未登入進入登入頁，已登入進入聊天頁。
14. 登出後需清除前端 session 資訊並導向登入頁。
15. 使用者需可更新顯示名稱，更新後聊天介面與設定頁需顯示新名稱。

### 2.4 管理員權限
1. 系統需提供管理員帳號角色（系統角色代稱：`system_admin`）。
2. 管理員僅可執行系統設定與使用者個人權限設定。
3. 管理員不可直接參與任何聊天對談功能（包含一對一與群組對談）。
4. 初始管理員帳號可建立其他管理員帳號。

### 2.5 裝置辨識與設備確認
1. 系統需支援網頁端裝置辨識，建立可追蹤之 `device_id`。
2. `device_id` 可由前端首次進站產生（如 UUID）或由後端簽發，並由瀏覽器保存（Cookie 或 Local Storage）。
3. 系統需在登入或重要操作時記錄裝置資訊，至少包含：
   - `device_id`
   - `user_agent`
   - `ip`
   - `first_login_at`
   - `last_login_at`
4. 系統需可標記裝置是否為信任裝置（`is_trusted_device`）。
5. 管理員需可查詢使用者最近登入裝置紀錄（僅查詢，不可用管理員身分參與聊天）。
6. 新裝置設為信任裝置時，需由帳號本人透過既有信任裝置授權，或由管理員授權。

### 2.6 使用者個人 IP 白名單
1. 系統需支援以「使用者帳號」為單位設定個人 IP 白名單規則。
2. 使用者登入時，系統需檢查來源 IP 是否符合其個人白名單。
3. 若來源 IP 不符合白名單，系統必須拒絕登入。
4. 拒絕登入時，系統需回覆明確錯誤原因（例如：`IP_NOT_ALLOWED`、`目前登入 IP 不在白名單中`）。
5. 個人 IP 白名單設定僅可由具權限者（管理員或被授權角色）維護。
6. 白名單規則需同時支援單一 IP 與 CIDR。
7. 白名單規則需同時支援 IPv4 與 IPv6。
8. 使用者未自訂白名單時，預設規則為允許所有 IP 登入。
9. IP 白名單管理介面需支援逐筆輸入規則，讓一般使用者可直接維護單一 IP。
10. IP 白名單需提供「一律放行」選項；啟用時略過白名單比對。

### 2.7 聊天系統管理後台
1. 系統需提供獨立於聊天室前台的管理後台登入入口。
2. 管理後台登入成功後需導向 `/office`，未登入或 session 過期時需導回 `/admin/login`。
3. 管理後台需提供使用者管理頁，可查詢 `users` 資料並顯示帳號、暱稱、Email、狀態、來源與最近在線時間。
4. 使用者管理頁需支援帳號、暱稱、Email、狀態、來源、建立日期與排序條件。
5. 管理後台 API 必須驗證 session token 與 `system_admin` 權限。
6. 管理後台需預留對話管理與管理員管理功能。
7. 管理後台各功能頁應具有清楚的路由、模板與前端程式責任，避免所有頁面長期集中在單一檔案。
8. 不同管理頁面的表格欄位、順序與寬度應可由各頁設定，不應依賴全站共用的欄位序號樣式。

## 3. 介面需求（Web）
1. 系統為網頁版（Browser-based）。
2. 前端介面需支援手機版全畫面（Mobile Fullscreen）。
3. 前端介面需支援電腦版全畫面（Desktop Fullscreen）。
4. 前端介面需支援可嵌入其他系統頁面的小浮動聊天視窗（Embedded Floating Chat）。
5. 主要頁面至少包含：
   - 對話列表
   - 對話視窗
   - 檔案 / 圖片上傳入口
   - 左側輔助導覽與設定入口
   - 系統管理後台的使用者、對話與管理員管理入口
6. 電腦網頁版版面配置需參考 WhatsApp Web 的使用布局（左側對話列表、右側對話內容區）。
7. 手機網頁版畫面與操作流程需參考 WhatsApp 手機 App 的布局邏輯（以單欄為主、對話清單與對話頁切換）。
8. 嵌入式浮動視窗需能以小尺寸模式顯示未讀、展開對話、收合與最小化。
9. 嵌入式浮動視窗需能插入其他系統頁面，但仍使用本系統的登入、權限與聊天 API。
10. 不為 ERP 或任何單一外部系統設計專屬界面版本。
11. 介面僅參考布局與互動邏輯，不得直接複製 WhatsApp 商標、圖示素材或品牌識別元素。
12. 介面需支援三語系：簡體中文、繁體中文、英文。
13. 桌機版左欄可包含輔助操作與設定入口；登入後左上角選單第一列需顯示目前登入帳號，點擊後進入設定頁。
14. 桌機版可提供聊天室分類列，顯示於左側對話列表上方。
15. 桌機版左欄上方需提供搜尋入口，可搜尋使用者與聊天記錄。
16. 搜尋使用者時，結果需以實際存在的使用者為準，不應直接把輸入值當成可建立對話的使用者。
17. 點選搜尋到的使用者後，若已有既有一對一對話需直接載入既有對話；若尚未建立，則可先開啟暫存聊天畫面，實際一對一對話可在送出第一則訊息時建立。
18. 桌機版訊息輸入區需提供附件按鈕選單，讓使用者可從輸入區直接選擇圖片或文件；選檔後需先顯示預覽視窗，並可輸入說明文字後送出；可一次選取多個檔案，送出後需保留在同一則訊息中；說明文字區一開始顯示一行，最多顯示六行後可捲動查看。
19. 桌機版對話區需支援拖拉圖片或檔案上傳；拖入時需顯示文件 / 照片兩個上傳區，放開後需進入附件預覽與送出流程；多檔拖拉上傳需以同一則訊息送出。
20. 桌機版訊息泡泡右鍵選單需參考 Telegram Web 的互動形式，顯示操作項目，且捲動訊息區時關閉；收回需以 `is_recalled` 狀態隱藏訊息，不應實體刪除訊息資料；引用回覆預覽需整合在同一個輸入框區塊內。當回覆已含引用的訊息時，預覽只應取該訊息本身內容，不應帶入更早引用鏈；左側對話列表的最後訊息預覽也只應顯示回覆正文，不顯示引用前綴與引用內容。

### 3.1 桌機版補充需求（目前原型方向）
1. 桌機版左上角可提供選單入口，切換左欄子頁內容。
2. 左欄設定頁可包含頭像管理與聊天室分類管理。
3. 聊天室分類至少需有預設分類 `ALL`，表示顯示全部對話。
4. 聊天室分類可先以前端暫存方式驗證互動，再逐步接正式後端設定 API。
5. MVP 階段可先以瀏覽器 `localStorage` 保存聊天室分類與分類內對話對應，供流程驗證與 UI 測試使用。
6. 若進入正式版或接近正式環境驗證，聊天室分類需改由後端資料表與設定 API 保存，前端不應再以本機暫存作為唯一資料來源。
7. 設定頁需參考 Telegram Web 的資訊架構：個人資料區置中顯示大頭貼、名稱與狀態，資料列顯示來源與帳號。
8. 編輯個人資料頁需以確認按鈕提交變更，未修改時不顯示提交按鈕。
9. 大頭貼功能未完成前，編輯頁需明確提示開發中，且不可進行實際上傳。
10. 聊天室分類與新建資料夾流程可參考 Telegram Web：包含資料夾說明、資料夾名稱與包含的聊天室選擇。
11. 新建與編輯資料夾頁面右上不需顯示更多選單；既有資料夾刪除可保留在分類清單中的資料夾操作選單。

## 4. 開發範圍與存取方式
1. 本系統開發需以 Go 專案為主體，並包含 HTML 前端頁面製作。
2. 系統需提供 API 存取介面，供外部系統與前端串接。
3. 系統需提供電腦網頁版全畫面使用介面。
4. 系統需提供手機網頁版全畫面使用介面。
5. 系統需提供可嵌入其他系統頁面的小浮動聊天介面。
6. 四種聊天存取方式（API / 電腦網頁 / 手機網頁 / 嵌入式浮動視窗）需對應同一套帳號與權限邏輯。
7. 管理後台使用同一套 session 與角色資料，但需與聊天介面分離，且僅允許 `system_admin` 使用。

## 5. 非功能性需求（基本）
1. 系統需具備基本權限控管，未登入者不可使用聊天功能；未登入或 session 過期時，`/home` 與 `/chat` 需導向 `/login`。
2. 檔案上傳需有基本限制（檔案大小上限、可接受副檔名）。
3. 系統需保留基本操作與錯誤日誌（供問題排查）。
4. 需求以「先可上線運作」為優先，後續再擴充進階功能。
5. 角色權限需明確區分：管理員角色與聊天使用者角色不可混用。
6. 裝置辨識需明確標示為「網頁可追蹤識別」，非實體硬體唯一識別碼。
7. 若使用者清除瀏覽器資料（Cookie / Local Storage）或更換瀏覽器，系統可視為新裝置。
8. 登入驗證流程需可記錄 IP 白名單比對結果與拒絕原因（供稽核與排查）。
9. 聊天訊息與檔案留存期間為 3 個月，超過留存期可由系統依規則清理或封存。
10. MVP 前端文案先以簡體中文為主，先建立三語系框架，不要求本階段完成完整翻譯定稿。
11. 外部系統接入驗證規格需保有文件化說明，至少包含 header、簽章字串格式、timestamp 規則與錯誤碼。

## 6. 本階段交付範圍（MVP）
1. Web 聊天介面（桌機全畫面 + 手機全畫面 + 嵌入式浮動視窗）。
2. 一對一聊天與群組聊天。
3. 文字、圖片、檔案傳送（圖片、Office / OpenDocument / iWork 文件、純文字資料與常見壓縮檔）。
4. 外部系統自動註冊與自動登入 API。
5. 裝置辨識與登入裝置紀錄（含 `device_id`）。
6. 使用者個人 IP 白名單登入限制與錯誤訊息回覆。
7. Go 專案內整合 HTML 前端與 API，提供桌機版、手機版與嵌入式浮動視窗存取。
8. 三語系介面（簡中 / 繁中 / 英文）。
9. 訊息與檔案留存 3 個月策略。
